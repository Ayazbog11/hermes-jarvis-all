# Changelog

## 2.1.4 — Разбор свежего `doctor --fix` после 2.1.3: причина отказа задач Планировщика теперь видна пользователю, диагностика "мёртвого" локального LLM-сервера

Пользователь обновился до 2.1.3 и прислал новый вывод `jarvis doctor --fix`: починка из 2.1.3
сработала правильно (теперь честно показывает «зарегистрировано только 1 из 4», а не молчаливое
«ок»), но всё ещё не называла ПРИЧИНУ, по которой `JARVIS-HUD`/`JARVIS-Gateway`/`JARVIS-App` не
регистрируются — только общий совет переустановить. В том же логе видно вторую, отдельную
причину, почему ассистент не отвечает: `model.provider=custom` указывает на
`http://localhost:9655/v1` (локальный OpenAI-совместимый сервер, судя по логу — что-то вроде
LM Studio/собственного прокси с моделью `deepseek-chat`), который не запущен — Hermes получает
`WinError 10061 (Connection refused)` на каждый чат-запрос.

- **`scripts/doctor.py::check_launchd()`**: при неудачной попытке самолечения теперь вытаскивает
  и показывает построчный вывод `setup_scheduled_tasks.py install` (`✔/✖ <имя задачи>: <причина
  schtasks>`) именно для недостающих задач — вместо общего «переустановите install.ps1», теперь
  видно настоящее сообщение об ошибке от `schtasks.exe` для каждой конкретной задачи.
- **`scripts/doctor.py::check_model()`**: отдельно распознаёт признаки "локальный сервер не
  запущен" (`Connection error`, `WinError 10061`, `ECONNREFUSED` и т.п.) и даёт релевантную
  подсказку («проверьте, что локальный LLM-сервер запущен, либо переключитесь на облако:
  `hermes model`») вместо общего совета «проверьте ключ провайдера и баланс», который не имеет
  смысла для локального `provider=custom`.
- Список задач в `check_launchd()` теперь также синхронизирован с `setup_scheduled_tasks.TASKS`
  (см. 2.1.3), это изменение продолжает ту же линию: чинить симптом «доктор не помогает».

## 2.1.3 — `jarvis doctor --fix` не чинил Gateway/HUD, когда Scheduled Tasks зарегистрировались лишь частично

Пользователь прислал новый `need.txt`/скриншот: HUD-чат показывал
`Hermes API недоступен: WinError 10061` (порт :8642 отказывает в соединении), а
`jarvis doctor --fix` был бессилен, хотя formально отрабатывал без ошибок. В том же логе
`jarvis status` показал `автозапуск: 1 задач(и) в Планировщике` — из 4 ожидаемых задач
(`JARVIS-HUD`, `JARVIS-Gateway`, `JARVIS-Updater`, `JARVIS-App`) реально зарегистрировалась
только одна.

**Причина — в `scripts/doctor.py::check_launchd()` (Windows-ветка).** Проверка сверяла список
найденных задач с ожидаемым, но самолечение (`setup_scheduled_tasks.py install`) запускалось
только строго при условии `if not tasks:` — то есть когда задач не было вообще НИ ОДНОЙ. Если
зарегистрировалась хотя бы одна из четырёх (ровно случай пользователя: `JARVIS-Updater` не
использует `RestartOnFailure` и потому не задевался уже починенным в 2.1.2 багом с
`Count=999`/`Count=255`, а остальные три — используют, и на момент установки у пользователя ещё
могли падать), `doctor` считал это полным успехом («1 задач(и) в планировщике» — без сравнения
с ожидаемым числом) и НЕ пытался дорегистрировать недостающие три. В результате Gateway и HUD
не поднимались сами при входе в систему, а `jarvis doctor --fix` не помогал, потому что
условие возврата в «самолечение» никогда не срабатывало.

- **`scripts/doctor.py::check_launchd()`**: теперь сверяет найденные задачи с полным списком из
  `setup_scheduled_tasks.TASKS` (единый источник истины вместо задублированного литерала) и
  запускает `setup_scheduled_tasks.py install` при ЛЮБОЙ недостаче (1–4 из 4), а не только при
  полном отсутствии. После починки заново проверяет полный набор и явно называет, каких задач
  всё ещё не хватает, если `install` не смог зарегистрировать все.
- Диагностика при неполном самолечении теперь подсказывает конкретную команду
  (`schtasks /Query /TN <имя> /V /FO LIST`) для просмотра причины отказа конкретной
  недостающей задачи, а не только общий совет переустановить.
- Напоминание пользователю: если провайдер модели показывает `nous` и `version: 2.1.1` (как в
  этом логе) — это уже исправлено в 2.1.2 (`Test-ModelPing`, проверка `model.provider`,
  запрос ключа OpenRouter); нужно обновиться (`jarvis update` или `install.ps1 -Yes`), чтобы
  подтянуть оба фикса.

## 2.1.2 — Разбор реального agent.log после 2.1.1: модель по умолчанию тихо падала через Nous Portal (Cloudflare 403), команда `/focus` конфликтовала со встроенной командой Hermes

Пользователь прислал `agent.log` с реальной Windows-машины: JARVIS, установленный по 2.1.1,
не отвечал ни на одно сообщение с первого хода сессии. Разбор лога показал сразу два независимых
бага, а не один.

**1. Модель по умолчанию (`upstage/solar-pro4:free`) фактически шла через провайдер `nous`
(`inference-api.nousresearch.com`), а не через `openrouter`, как задумано** — несмотря на то,
что `install.ps1` явно выполняет `hermes config set model.provider openrouter` перед установкой
модели. Шлюз Nous в момент установки был заблокирован Cloudflare (`403 Attention Required`) —
каждый запрос падал молча, ассистент никогда не отвечал. Причина в самом `install.ps1`: ветка
«настраиваем модель по умолчанию» проверяла успех только чтением `hermes config get model`
(совпадает ли имя модели), но никогда не проверяла (а) что `model.provider` реально стал
`openrouter`, и (б) что модель в принципе отвечает — эта проверка (`hermes chat -q`) была только
в соседней ветке «модель уже была настроена». В итоге install.ps1 печатал «✔ модель по умолчанию»
даже когда реальный первый запрос гарантированно проваливался.

- **`install.ps1`**: ветка установки модели по умолчанию теперь а) проверяет читаемый
  `model.provider` (не только `model`), б) реально пингует модель через `hermes chat -q` с общей
  функцией `Test-ModelPing` (расширенный список маркеров ошибки: `attention required`,
  `cloudflare`, `permissiondeniederror` — в дополнение к кодам `401/403/405/429`), и в) если
  ключ OpenRouter не задан, сразу предлагает его ввести (со ссылкой на `openrouter.ai/keys`) —
  бесплатные модели с суффиксом `:free` всё равно требуют бесплатный ключ OpenRouter, просто без
  оплаты; раньше об этом сообщалось только постфактум, после того как первый чат уже падал.
- **`scripts/doctor.py::check_model()`**: тот же расширенный список маркеров ошибки в проверке
  ping — `hermes doctor` теперь ловит именно этот сценарий (Cloudflare-блок апстрима) явным
  диагнозом, а не общим «не отвечает».
- **`docs/TROUBLESHOOTING.md`**: добавлена строка с описанием именно этого сценария
  (`provider=nous`, `Attention Required`, `Cloudflare`) и командами для исправления
  (`hermes config get model.provider`, `hermes config set model.provider openrouter`,
  `hermes config set OPENROUTER_API_KEY`).

**2. Slash-команда `/focus` плагина `jarvis-core` (переключение режима JARVIS: focus/night/
presentation) молча переставала работать** на любой более новой версии Hermes Agent, которая
добавила собственную встроенную команду `/focus` (переключатель отображения хода агента в CLI,
никак не связанный с режимами JARVIS). Лог явно показывает: `Plugin 'jarvis-core' tried to
register command '/focus' which conflicts with a built-in command. Skipping.` — Hermes отдаёт
приоритет встроенной команде и тихо пропускает регистрацию нашей, без единой видимой ошибки
в чате.

- **`plugins/jarvis-core/__init__.py`**: команда переименована в `/mode` (`/mode`,
  `/mode off`, `/mode night`, `/mode presentation`) — не пересекается ни с одной встроенной
  командой Hermes. Инструмент `jarvis_mode` и вся остальная логика режимов не изменились.
- **`docs/USAGE.md`, `docs/ARCHITECTURE.md`, `bin/jarvis`, `bin/jarvis.ps1`**: обновлены все
  упоминания `/focus` → `/mode` (голосовая подсказка при старте, таблица slash-команд, карта
  архитектуры).
- **`tests/test_plugins.py`**: обновлён тест регистрации команд под новое имя.

## 2.1.1 — Багфиксы по итогам реальной установки 2.1.0: убрана нерабочая кнопка обновления HUD, починен Telegram, дефолтная модель, Scheduled Tasks, доктор

Пользователь установил 2.1.0 на реальной машине и сообщил о серии проблем: (1) кнопка обновления
в HUD никогда не работала (`update.py` ждёт позиционный аргумент `check`, а HUD слал `--check`) —
попросил убрать её из кода полностью, а не чинить; (2) Telegram не подключался, HUD показывал
«telethon не установлен», хотя install-лог печатал «✔ telethon установлен»; (3) хотел
`upstage/solar-pro4:free` моделью по умолчанию; (4) Scheduled Tasks (JARVIS-HUD/Gateway/App) не
регистрировались при установке (Access Denied), из-за чего gateway API был недоступен
(`WinError 10061`); (5) виджет «Модель ИИ» в HUD иногда показывал буквально «not found».

- **HUD: кнопка обновления убрана из кода полностью** (`hud/static/index.html`, `hud/server.py`) —
  по прямому запросу пользователя, а не патч бага. Убраны `#updChip`, обработчик клика
  `startUpdate()`, SSE-слушатель `update.progress`, эндпоинты `GET /api/update` и
  `POST /api/update/check|apply|rollback`, метод `_update_status()`/`_update_action()` и связанный
  воркер-поток. Автоматическое/плановое обновление по расписанию (`JARVIS-Updater`, `update.py auto`)
  не тронуто и продолжает работать как раньше — убран только ручной REST-путь через HUD.
  Обновляться теперь можно из терминала: `jarvis update --check`, `jarvis update`,
  `jarvis update --status` (см. `docs/USAGE.md`).
- **Telegram: настоящая причина ложного «telethon не установлен»** — `install.ps1`'s `Invoke-Pip`
  ставил пакеты через `uv pip install` без явного `--python`, полагаясь только на
  `$env:VIRTUAL_ENV`; если эта переменная в сессии PowerShell была выставлена на что-то другое
  раньше (повторный запуск install.ps1, унаследованная переменная и т.п.), `uv` мог тихо поставить
  telethon в другой Python, чем тот, из-под которого реально работает HUD (`$VenvPy`) — установка
  рапортовала успех, а HUD всё равно не видел пакет. Исправлено: `uv pip install` теперь всегда
  получает явный `--python $VenvPy`. Дополнительно `jarvis doctor` (и `--fix`) теперь проверяют
  импортируемость telethon именно тем интерпретатором, который использует HUD (новая проверка
  «Telegram (telethon)»), чтобы это расхождение сразу было видно, а не терялось в логах установки.
- **Модель по умолчанию — `upstage/solar-pro4:free`** (`install.ps1`) — если модель ещё не
  настроена, установщик теперь сам выставляет бесплатную модель Upstage Solar Pro 4 через
  OpenRouter (не требует платной подписки, чтобы JARVIS отвечал сразу после установки), вместо того
  чтобы сразу открывать интерактивный мастер выбора провайдера. Мастер по-прежнему доступен в любой
  момент через `hermes model`.
- **Scheduled Tasks: Access Denied и решение** — `scripts/doctor.py::check_launchd()` на Windows в
  режиме `--fix` вызывал `setup_scheduled_tasks.py` вообще без подкоманды (обязательный позиционный
  аргумент `{install,remove,status}`), из-за чего вызов гарантированно падал с ошибкой argparse
  (код возврата 2) и `jarvis doctor --fix` никогда не пытался реально переустановить задачи.
  Исправлено — теперь передаётся `install --home <HERMES_HOME> --python <sys.executable>`.
- **`scripts/setup_scheduled_tasks.py`: кракозябры в тексте ошибок `schtasks`** — вывод `schtasks`
  на русской Windows идёт в кодировке OEM (обычно cp866), а декодировался как UTF-8/локаль по
  умолчанию — сообщения об ошибке (включая Access Denied) отображались нечитаемой кашей. Исправлено
  явным декодированием OEM-кодовой страницы на Windows.
- **`bin/jarvis.ps1`: PowerShell-баг с срезами массивов ломал `jarvis update --check`/
  `brain sql --rw`** — при передаче единственного строкового аргумента через `@Rest` PowerShell 5.1
  в некоторых путях разворачивал строку в массив символов, из-за чего срез `[1..($Rest.Count-1)]`
  давал не то, что ожидалось. Добавлена вспомогательная функция `Tail()`, корректно возвращающая
  «хвост» аргументов независимо от того, массив это или скаляр.
- **HUD «Модель ИИ»** (`scripts/model_switch.py`) — добавлена защитная фильтрация
  (`_clean_config_value()`) на случай, если `hermes config get` вернёт текстовый маркер
  отсутствующего значения (например, «not found»/«not set») вместо пустой строки — такое значение
  теперь трактуется как «модель не настроена», а не показывается пользователю буквально. Та же
  защита добавлена и в `scripts/doctor.py::check_model()`.
- **Убран стухший баннер про Outlook в `install.ps1`** — инструкция в конце установки ещё
  упоминала Outlook/COM (уже полностью убранный в 2.1.0), теперь указывает на
  `jarvis calendar setup` (Google Calendar).

## 2.1.0 — Убран Outlook (всплывающие окна), починен PowerShell-баг ломавший gateway/HUD/автообновление, не работавшая смена модели в HUD, кнопка обновления и сворачиваемые виджеты в HUD, `jarvis uninstall`

Пользователь сообщил о нескольких проблемах разом: (1) `jarvis gateway` падал с ошибкой `NativeCommandError`
на `schtasks`; (2) окно регистрации Outlook всплывало каждые пару минут само по себе; (3) в HUD
нет кнопки обновления, и боковые панели с виджетами нельзя ни прокрутить, ни скрыть лишнее; (4) в HUD
нельзя поменять модель ИИ; заодно попросил команду для полного удаления + переустановки.

- **Критический баг PowerShell 5.1, ломавший `jarvis gateway`/`jarvis hud`/автообновление**
  (`bin/jarvis.ps1`, `install.ps1`, `scripts/setup_cron.ps1`) — при `$ErrorActionPreference = "Stop"`
  Windows PowerShell 5.1 (в отличие от pwsh 7+) считает **любой** байт, написанный внешней программой
  (`schtasks.exe`, `winget.exe`, `hermes.exe`…) в stderr, **завершающей скрипт ошибкой**, даже если он
  тут же отбрасывается через `2>$null`/`2>&1` — это давний баг самого PowerShell
  ([PowerShell/PowerShell#3996](https://github.com/PowerShell/PowerShell/issues/3996)), исправленный
  только в pwsh 7.2+ и то не по умолчанию. `jarvis gateway` (и множество других команд) падали на
  первом же вызове `schtasks /Query` для ещё не созданной задачи — обычная, ожидаемая ситуация.
  Добавлена функция-обёртка `Quiet { ... }`, временно снижающая `ErrorActionPreference` только на
  время вызова внешней программы и гарантированно восстанавливающая его сразу после (даже при
  исключении) — применена ко всем вызовам `schtasks`/`winget`/`hermes`/`curl.exe`/`uv` с `2>`.
- **Полностью убрана интеграция с Outlook (COM)** — `win_calendar`/`win_contacts`
  (`plugins/jarvis-windows/tools.py`, `schemas.py`, `plugin.yaml`) и Outlook-фоллбэк календаря в
  HUD (`hud/sysinfo.py`) и watchdog (`plugins/jarvis-core/platform_compat.py::upcoming_events`).
  Причина: первое обращение к `New-Object -ComObject Outlook.Application` без настроенного профиля
  Outlook открывает мастер регистрации/окно первого запуска — а HUD дёргал этот код каждые
  несколько минут (`Collector.refresh`, безусловно, для виджета «Сегодня»), из-за чего окно
  всплывало заново и заново без единого действия пользователя. Единственный календарь JARVIS теперь
  — кроссплатформенный Google Calendar (`jarvis_calendar`, `jarvis calendar setup`); HUD «Сегодня» на
  Windows тоже переключён на него (`hud/sysinfo.py::_calendar_today_gcal`).
- **HUD: прямая кнопка обновления** — новые эндпоинты `GET /api/update`, `POST
  /api/update/check|apply|rollback` (`hud/server.py`), запускающие `update.py` напрямую (apply/rollback
  — в фоновом потоке с прогрессом через SSE-событие `update.progress`). Раньше кнопка «Обновление»
  в шапке лишь отправляла текст в чат («Обнови JARVIS…») в расчёте на то, что модель сама вызовет
  инструмент `jarvis_update` — теперь это явный REST-вызов; также строка «Доступно обновление» с
  кнопкой добавлена в виджет «Система».
- **HUD: сворачиваемые/скроллируемые боковые панели** — колонки виджетов (`#colL`/`#colR`) теперь
  сами скроллятся, если высота виджетов превышает экран (раньше `overflow:hidden` просто обрезал
  лишнее без возможности прокрутки). Новая кнопка «Виджеты» (иконка сетки) в шапке открывает список
  чекбоксов — какие карточки показывать; выбор сохраняется в `localStorage`, переживает перезагрузку.
- **`jarvis uninstall [--purge] [--yes]`** (`bin/jarvis.ps1`, `bin/jarvis`) — по запросу («сделай
  чтоб я мог полностью удалить и заново скачать»): останавливает все сервисы/автозапуск (Планировщик
  заданий на Windows, launchd/systemd на macOS/Linux), убирает cron-задачи Hermes, удаляет команду
  `jarvis` и весь `$HERMES_HOME` (без `--purge` — только плагины/HUD/скиллы/настройки JARVIS,
  сохраняя сам установленный Hermes Agent; с `--purge` — вместе с ним). Требует явного подтверждения
  (`да`) если не передан `--yes`.
- **Починена не работавшая смена модели ИИ в HUD** — `scripts/model_switch.py` и
  `plugins/jarvis-core/messenger.py` искали бинарник `hermes` только через `shutil.which("hermes")`
  (чистый PATH). На Windows это ненадёжно сразу по двум причинам: (a) HUD/gateway обычно запускаются
  из Планировщика заданий при входе в систему и могут унаследовать PATH, записанный ДО того, как
  `install.ps1` дописал в него `bin`-каталог Hermes (`[Environment]::SetEnvironmentVariable(...,
  "User")` подхватывают только новые процессы, а не уже запущенные); (b) самообновление Hermes через
  Desktop UI иногда удаляет `hermes-agent/bin`, не трогая PATH (известный апстрим-баг
  [NousResearch/hermes-agent#91563](https://github.com/NousResearch/hermes-agent/issues/91563)).
  В обоих случаях `hermes` физически установлен, но `shutil.which` возвращает `None`, и кнопки HUD

## 2.0.1 — Исправлен install.ps1: потерян BOM, установщик не запускался на Windows PowerShell 5.1

Пользователь сообщил, что `install.ps1` из релиза 2.0.0 падал с каскадом ошибок парсера
(«Отсутствует закрывающий знак `}`», «Непредвиденная лексема `)`» и т.д.) сразу на строках с
функциями `Ok`/`AskYN`/`WarnMsg`. Причина: файл каким-то образом лишился метки UTF-8 BOM в начале
(остался обычный UTF-8 без BOM). Встроенный в Windows `powershell.exe` (5.1, без BOM запускается
как `pwsh` не был — у пользователя именно 5.1) при отсутствии BOM читает `.ps1` в системной
однобайтовой кодировке (обычно cp1251), а не как UTF-8. Файл содержит кириллицу и юникод-стрелки
(▶ ✔ ⚠ ✖ … ─) прямо внутри строковых литералов — при неверном чтении многобайтовые
последовательности превращались в кавычки и другие спецсимволы, преждевременно обрывающие
строки и блоки `{ }`, отсюда и полный каскад ошибок синтаксиса.

- Восстановлен BOM (`EF BB BF`) в начале `install.ps1` — единственное изменение файла, содержимое
  не тронуто.
- Новый регрессионный тест `tests/test_release_audit.py::test_ps1_scripts_have_utf8_bom` —
  проверяет, что **все** `.ps1`-файлы в репозитории начинаются с BOM, чтобы эта проблема не могла
  повториться незаметно для CI на любом из скриптов (`install.ps1`, `bin/jarvis.ps1`, `get.ps1`,
  `scripts/setup_cron.ps1` и любые будущие).

  client id у Google Calendar) — разовая бесплатная настройка, см. `docs/TELEGRAM.md`.

- Существующий `jarvis_send_message`/`hermes send` (Bot API) не тронут — оба пути сосуществуют,

## 1.6.1 — повторы и «не заткнуть»
Отзыв: «несколько раз повторяет одно и то же, и то, что он говорит, невозможно остановить».

### Почему повторялось
- Ход агента приходил на HUD **тремя путями**: плагин `jarvis-core` (pre/post_llm_call), хук `jarvis-boot`
  (agent:start/end) и прокси `/api/chat`. Текст отрисовывался и озвучивался по несколько раз.
- Контекст «доступно обновление» подмешивался в **каждый** ход — модель послушно напоминала о нём каждый раз.
- Модель вызывала `mac_say` поверх TTS Hermes: одну фразу говорили два голоса, и `say` нельзя было прервать.

### Исправлено
- HUD-сервер отбрасывает дубли `turn.*/stream.*`, пока идёт чат через прокси; `jarvis-boot` больше не зеркалит ходы;
  HUD не озвучивает и не показывает один и тот же ответ дважды.
- Напоминание об обновлении — один раз за процесс.
- `mac_say`: новая фраза перебивает предыдущую; `action=stop` глушит `say`/`afplay`/озвучку HUD; описание инструмента
  запрещает использовать его для обычных ответов. SOUL.md и навык voice-etiquette: «ничего не повторяй», «стоп» = замолчать.

### Как остановить речь теперь
`Esc` или кнопка ■ в HUD · «Замолчать» в меню ◉ (⌘.) · `jarvis hush` в терминале · голосом «стоп»/«хватит»
(барж-ин Hermes: просто начните говорить).
