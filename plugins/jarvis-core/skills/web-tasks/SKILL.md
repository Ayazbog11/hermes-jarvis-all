## When to Use
- Задача-поиск с критериями: «найди отель в Праге на выходные до 100€», «сравни цены на этот ноутбук»,
  «найди билеты Москва-Стамбул на пятницу», «что пишут про X» — то есть НЕ просто факт, а подбор/сравнение
  нескольких вариантов по условиям.
- «Проанализируй эту страницу» / «что тут написано» / «глянь на экран» — пользователь уже смотрит на
  что-то (открытая вкладка браузера или весь экран) и просит объяснить/оценить/перевести содержимое.

## Инструменты Hermes, которые уже есть — ничего изобретать не нужно
| Что нужно | Инструмент | Когда |
|---|---|---|
| Найти несколько кандидатов по запросу | `web_search` | Первый шаг почти всегда — быстрее и дешевле браузера |
| Прочитать конкретную страницу целиком | `web_extract` | Известен URL, страница статична/несложная |
| Страница требует логина / JS-рендеринга / формы / пагинации (booking-сайты, маркетплейсы) | `browser_navigate` → `browser_snapshot` → `browser_click`/`browser_type`/`browser_scroll` | Данные не приходят из `web_extract` (пустая/urезанная страница, редирект на логин) |
| Визуально понять страницу (капча, сложная вёрстка, картинки/скриншоты цен) | `browser_vision` (после `browser_navigate`) | Текстовый snapshot не даёт ответа |
| Пользователь уже смотрит на что-то на своём экране (не обязательно браузер) | Скриншот снимается сам через `screen_context` (фразы «на экране», «посмотри сюда» и т.п. — см. `jarvis-core/__init__.py:wants_screen`), затем `vision_analyze(path)` | «Что это за окно», «переведи это», «что за ошибка» |

## Procedure — задача-поиск («найди отель/билет/товар…»)
1. Раскладывай запрос на критерии сам, не переспрашивай очевидное (даты по умолчанию — ближайшие
   подходящие; бюджет/район уточняй, только если пользователь совсем не задал ориентир).
2. `web_search` с 2–3 разными формулировками запроса (разные сайты дают разные результаты) —
   собери 4–6 кандидатов с ценой/рейтингом/ссылкой.
3. Если `web_search`/`web_extract` не даёт достаточно деталей (цена скрыта за календарём дат,
   фильтрами, JS) — `browser_navigate` на конкретный сайт-агрегатор, `browser_snapshot`, заполни
   форму поиска (`browser_type`/`browser_click`), затем снова `browser_snapshot` или `browser_vision`
   по результатам.
4. Отвечай сравнительной таблицей из 3–5 лучших вариантов (название, цена, что важно по критериям
   пользователя) — не вываливай сырой список из 20 ссылок.
5. Не бронируй/не оплачивай ничего сам — только находишь и показываешь варианты; бронирование —
   с явным подтверждением пользователя на каждом шаге (см. SOUL.md, принцип «Необратимое — с
   подтверждением»).

## Procedure — анализ страницы/экрана
1. Если пользователь имел в виду браузерную вкладку и в разговоре уже упоминался/только что открывался
   конкретный URL — `browser_navigate` (если сессия не открыта) → `browser_snapshot` для текста,
   `browser_vision` для визуального контекста (макет, изображения, капча).
2. Если пользователь говорит о своём экране в целом (не обязательно браузер — может быть код, чат,
   ошибка ОС) — контекст `[JARVIS screen]` уже содержит путь к свежему скриншоту (см. `screen_context`
   в `jarvis-core`); сразу `vision_analyze(path)` с этим путём, не спрашивай «какой именно экран».
3. Отвечай сутью, а не пересказом всего текста страницы: что это, что важно, что можно сделать дальше
   (кнопка/ссылка/следующий шаг), если пользователь не попросил дословный перевод/транскрипцию.

## Pitfalls
- Не вызывай `browser_*` инструменты, если `web_search`/`web_extract` уже дал достаточный ответ —
  браузерная сессия медленнее и дороже.
- На сайтах с капчей/анти-бот защитой — `browser_vision`, чтобы увидеть капчу, но не пытайся её решать
  автоматически; сообщи пользователю, что сайт требует ручной проверки.
- Цены/наличие на сайтах бронирования быстро устаревают — предупреждай, что нужно перепроверить перед
  оплатой, если между поиском и решением пользователя прошло много времени.

## Verification
Ответ на задачу-поиск — сравнение конкретных вариантов с ценами/ссылками, не общие советы «поищите на
Booking.com». Ответ на «проанализируй страницу» — по существу того, что реально на странице/экране,
без домыслов о том, чего не видно.
